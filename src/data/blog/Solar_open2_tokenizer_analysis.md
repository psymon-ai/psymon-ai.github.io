## Table of contents

## 들어가는 글

많은 기대를 걸고 있는 Upstage사의 Solar-Open2 출시 소식을 접하고 가장 먼저 확인하고 싶었던 건 벤치마크 점수가 아니었습니다.

더 궁금했던 건 체감 한국어 성능이었습니다. 한국 파운데이션 모델을 표방하는 만큼, 실제로 써 봤을 때 문장이 얼마나 자연스러워졌는지 먼저 보고 싶었습니다. 잠깐 만져 본 인상은 꽤 좋았습니다. 이전 Solar 계열 모델보다 한국어 문장이 훨씬 부드러워졌고, 답변의 호흡도 더 안정적으로 느껴졌습니다.

그런데 쓰다 보니 문득 잊고 있던 이슈가 하나 떠올랐습니다.

[Solar-Open-100B에서 보고된 토크나이저 이슈](https://arca.live/b/alpaca/158957246)입니다. 한국어 회계 용어처럼 긴 어절이 하나의 토큰으로 들어갈 때, 모델이 그 토큰의 의미를 안정적으로 처리하지 못하는 현상이었습니다. 단순히 한국어를 못한다거나 회계 지식이 부족하다고 말하기에는 묘했습니다. 같은 단어를 조금 다르게 쓰면 답이 정상으로 돌아왔기 때문입니다.

그래서 자연스럽게 궁금해졌습니다.

> 이 현상은 아직 남아 있을까?  
> 아니면 Solar-Open2에서는 어떻게 달라졌을까?  
> 만약 어떤 모델에서는 발생하고 어떤 모델에서는 발생하지 않는다면, 차이는 어디서 오는 걸까?

처음에는 단순한 재현 실험으로 시작했습니다. 그런데 조사하다 보니 이 현상은 생각보다 흥미로웠습니다. 하나의 프롬프트 예외나 일회성 hallucination이라기보다, 토크나이저 학습 코퍼스, 도메인 데이터 비율, BPE merge rank, long-tail token embedding이 한꺼번에 얽힌 현상처럼 보였습니다.

이번 글은 그 과정을 정리한 분석 리포트입니다.
Solar-Open2에서 느낀 개선은 분명했고, 그래서 오히려 이런 작은 경계 조건까지 살펴볼 가치가 있다고 느꼈습니다.

## 처음 본 현상

출발점이 된 표현은 `법인세효과가`입니다.

한국어 회계 문서에서 아주 낯선 표현은 아닙니다. 예를 들어 법인세 효과, 이연법인세 효과, 법인세비용 같은 단어는 회계 세무 문맥에서 자주 나옵니다. 하지만 일상 한국어에서 자주 쓰는 말은 아닙니다. 더구나 `법인세효과가`처럼 띄어쓰기 없이 조사까지 붙은 형태는 일반 대화에서는 거의 나오지 않습니다.

현상은 이 표현이 문장 중간에 들어갈 때 나타납니다.

```text
어떤 경우 법인세효과가 있을까?
```

사람은 당연히 이렇게 이해합니다.

```text
어떤 경우 [법인세 효과]가 있을까?
```

그런데 보고된 Solar-Open-100B 답변은 법인세 문맥으로 가지 않았습니다.

```text
에너지 절감 효과가 나타날 수 있는 대표적인 경우는 다음과 같습니다.
...
```

질문은 법인세 효과를 묻고 있는데, 답변은 에너지 절감 효과 쪽으로 이동했습니다. 단순히 회계 지식이 부족해서라기엔 이상했습니다. 같은 질문을 한 칸 띄어 쓰면 답변이 정상으로 돌아오기 때문입니다.

```text
어떤 경우 법인세 효과가 있을까?
```

핵심은 단순한 오타나 회계 지식 부족이 아니었습니다. 특정 문자열이 특정 tokenization path를 탈 때 `법인세`라는 단서를 제대로 활용하지 못하는 경로가 생긴다는 점이었습니다.

처음에는 모델의 세무 지식 문제처럼 보였습니다. 하지만 곧 토크나이저 쪽으로 의심이 옮겨갔습니다.

## 어디까지 재현되는가

먼저 Upstage가 공개한 Hugging Face 모델과 tokenizer repository를 전수 조사했습니다. 조사 대상은 `upstage/models`에 공개된 24개 repository였습니다.

확인한 문자열은 주로 다음과 같습니다.

```text
 법인세효과가
 매도가능증권평가손익
```

여기서 앞의 공백은 중요합니다. Byte-level BPE 계열 토크나이저에서는 문장 중간의 단어가 보통 앞 공백을 포함한 형태로 토큰화되기 때문입니다. GPT 계열 토크나이저에서 ` word`와 `word`가 다른 토큰인 것과 같은 구조입니다.

전수 조사 결과 같은 tokenization 조건은 두 repository에서 확인됐습니다.

| 모델 또는 tokenizer | ` 법인세효과가` tokenization |
|---|---|
| `upstage/Solar-Open-100B` | `[195496]` 단일 토큰 |
| `upstage/solar-pro3-tokenizer` | `[195496]` 단일 토큰 |
| `upstage/solar-pro2-tokenizer` | `[' 법인세', '효과가']` |
| `SOLAR-10.7B` 계열 | 여러 토큰으로 분해 |
| TinySolar 계열 | 여러 토큰으로 분해 |

Solar-Pro3 모델 자체의 weight는 공개되어 있지 않지만, `solar-pro3-tokenizer`는 공개되어 있었고 Solar-Open-100B와 동일한 단일 토큰을 가지고 있었습니다.

이 시점에서 확인할 질문은 더 구체적으로 바뀌었습니다.

> Solar-Pro3 tokenizer가 같은 token path를 가지고 있다면, 실제 Solar-Pro3 답변도 같은 방식으로 달라질까?

그래서 Console에서 직접 실험했습니다.

## Upstage Console에서 재현

Console에서 가장 먼저 실행한 질문은 이것이었습니다.

```text
어떤 경우 법인세효과가 있을까?
```

공개된 Solar-Pro3 tokenizer 기준으로 이 문장은 다음처럼 들어갑니다.

```text
[41170, 5577, 195496, 51490, 4126]
= ['어떤', ' 경우', ' 법인세효과가', ' 있을까', '?']
```

여기서 눈에 띄는 부분은 `[195496]`입니다. 이 하나의 토큰이 ` 법인세효과가` 전체를 담당합니다.

Console 답변은 이렇게 시작했습니다.

```text
잘 이해하지 못했어요!

“Kami”가 어떤 의미인지 정확히 알려주시면,
해당 상황에 대해 자세히 설명해 드릴 수 있어요.
```

반대로 대조군은 정상입니다.

```text
어떤 경우 법인세 효과가 있을까?
```

이 문장은 다음처럼 들어갑니다.

```text
[41170, 5577, 9915, 23183, 51490, 4126]
= ['어떤', ' 경우', ' 법인세', ' 효과가', ' 있을까', '?']
```

이번에는 ` 법인세`와 ` 효과가`가 분리됩니다. 이 경로에서는 모델이 법인세 문맥에 맞는 답변을 출력합니다.

```text
법인세 효과란?
법인세(소득세) ​효과​는 기업이 회계상 발생시킨 이익에 대해 실제로 납부해야 할 세금이 회계상 비용과 어떻게 연결되는지를 의미합니다. 회계에서는 ​법인세 비용​ · ​법인세 부채​ · ​이연법인세​ 등이 기록되고, 세무에서는 ​과세소득​, ​세액 공제·감면​, ​세금 손실 이월​ 등이 적용됩니다. 이 두 영역이 일치하지 않을 때 ​세무‑회계 차이​(temporary difference, permanent difference)가 발생하고, 그 차이가 재무제표에 법인세 효과를 만들어 줍니다.
```

또 다른 대조군도 있습니다.

```text
법인세효과가 발생하는 경우를 설명해줘.
```

이 경우 `법인세효과가`가 문장 처음에 오기 때문에 앞 공백이 없습니다. 토크나이저는 다음처럼 분해합니다.

```text
[7131, 32372, 11049, 23502, 49330, 38635, 4109]
= ['법인세', '효과가', ' 발생하는', ' 경우를', ' 설명해', '줘', '.']
```

이 경우도 답변은 정상입니다.
```text
법인세 효과가 발생하는 경우
(법인세 = 기업(법인)이 매년 발생하는 소득에 대해 납부해야 하는 소득세)

법인세 효과는 ​“세금이 회계·세무 양쪽에서 어떻게, 언제, 어느 정도 영향을 미치는가”​ 를 의미합니다.
아래에서는 ​회계상​(재무제표·법인세 회계)과 ​세무상​(세법·세무조정) 두 관점에서 법인세 효과가 나타나는 대표적인 상황을 정리하고, 실제 기업·경영 의사결정에 어떤 의미를 갖는지 설명합니다.
```

따라서 현상은 단순합니다.

```text
앞 단어 뒤에 일반 공백이 붙은 경우
-> ' 법인세효과가'
-> [195496]
-> 의미 이탈

문장 처음에 오거나 명시적으로 띄어 쓴 경우
-> '법인세' + '효과가'
-> 의미 유지
```

## 공백 하나가 왜 이렇게 크게 작용할까

처음에는 이상하게 느껴집니다. 공백 하나 때문에 `법인세`라는 단서가 흐려진다니, 너무 민감해 보입니다. 하지만 BPE 관점에서 보면 이건 같은 단어가 아닙니다.

Solar-Pro3 tokenizer는 custom byte-level BPE입니다. normalizer는 `None`이고, pre-tokenizer는 공백을 보존합니다. 일반 ASCII space는 뒤따르는 단어와 함께 하나의 span으로 들어갑니다.

실제 문장을 보겠습니다.

```text
새로운 법률 해석에 따르면 법인세효과가
```

pre-tokenizer는 마지막 부분을 이렇게 잡습니다.

| offset | original slice |
|---:|---|
| `[14, 21]` | ` 법인세효과가` |

즉 문장 안의 `법인세효과가`는 bare `법인세효과가`가 아니라, 앞 공백을 포함한 ` 법인세효과가`입니다.

이제 BPE merge rank를 보면 왜 결과가 갈리는지 알 수 있습니다.

| pair | merge rank | 결과 |
|---|---:|---|
| ` 법인세` + `효과` | 25,233 | ` 법인세효과` |
| `효과` + `가` | 28,020 | `효과가` |
| ` 법인세효과` + `가` | 191,144 | ` 법인세효과가` |
| `법인세` + `효과` | 45,360 | `법인세효과` |
| `법인세효과` + `가` | 없음 | 없음 |
| `법인세` + `효과가` | 없음 | 없음 |

문장 처음에 오는 bare 형태는 이렇게 갑니다.

```text
법인세효과가
-> '법인세' + '효과' + '가'
-> '법인세' + '효과가'
-> [7131, 32372]
```

`효과 + 가` merge가 먼저 일어나고, 그 뒤 `법인세 + 효과가`를 합치는 merge가 없기 때문입니다.

반대로 앞 단어 뒤에 이어지는 선행 공백 형태는 이렇게 갑니다.

```text
' 법인세효과가'
->'  법인세' + '효과' + '가'
->'  법인세효과' + '가'
->'  법인세효과가'
-> [195496]
```

` 법인세 + 효과`의 rank가 `효과 + 가`보다 빠르기 때문에 ` 법인세효과`가 먼저 만들어집니다. 그리고 아주 늦은 merge인 rank 191,144에서 `가`까지 붙어 `[195496]`가 됩니다.

여기서 중요한 점은 `[195496]`가 vocab의 거의 끝에 있는 tail token이라는 사실입니다. vocab size는 196,608이고, 이 토큰의 ID는 195,496입니다. merge rank도 191,144로 매우 늦습니다.

즉 이 토큰은 자주 쓰이는 중심 토큰이라기보다, 큰 vocab의 말단에 들어간 긴 도메인 어절에 가깝습니다.

## Long-tail token이 민감해지는 이유

토크나이저 학습에서 어떤 문자열이 하나의 토큰이 되었다고 해서, 모델이 그 의미를 충분히 배웠다는 뜻은 아닙니다.

BPE는 기본적으로 빈도 기반입니다. 어떤 문자열 조각이 반복해서 등장하면 merge 후보가 됩니다. 하지만 tokenizer 학습 corpus에서 merge될 만큼 등장했다는 것과, 모델 pretraining/SFT에서 그 atomic token embedding이 충분히 학습되었다는 것은 전혀 다른 문제입니다.

특히 ` 법인세효과가` 같은 토큰은 주의가 필요합니다.

```text
 법인세효과가
```

이 토큰 하나가 `법인세`, `효과`, `가`를 모두 하나로 합칩니다. 모델 입장에서는 더 이상 `법인세`라는 잘 학습된 하위 토큰을 볼 수 없습니다. `[195496]`라는 하나의 embedding만 볼 뿐입니다.

반대로 분해된 경로에서는 해석이 더 안정적입니다.

```text
법인세효과가
법인세 + 효과가
법인세 + 효과 + 가
```

이 경우 모델은 `법인세`라는 비교적 명확한 의미 단위를 볼 수 있습니다. `효과`, `효과가`도 일반적으로 충분히 학습된 토큰입니다.

따라서 이 현상은 이렇게 정리할 수 있습니다.

> 긴 도메인 어절이 atomic tail token으로 합쳐지면 token count는 줄어든다.  
> 하지만 그 token embedding이 충분히 학습되지 않으면 semantic composition이 사라진다.

이번 사례에서는 바로 그 일이 일어난 것으로 보입니다.

## 다른 모델은 어땠나

이 현상이 한국어 모델 전반의 보편적인 문제인지도 확인했습니다. Gemma 4, Gemma 3, Qwen, Phi, EXAONE 계열 tokenizer를 같은 기준으로 비교했습니다.

Gemma 4의 경우 `법인세효과가`는 이렇게 분해됩니다.

```text
법인세효과가
-> 법 / 인 / 세 / 효 / 과 / 가

 법인세효과가
-> ▁법 / 인 / 세 / 효 / 과 / 가
```

Solar-Pro3처럼 ` 법인세효과가` 전체가 하나의 atomic tail token이 되지 않습니다.

동일한 기준으로 여러 tokenizer를 스캔하면 차이가 훨씬 선명합니다.

| tokenizer | 주의 후보 전체 | score ≥ 8 후보 | 도메인 힌트 |
|---|---:|---:|---:|
| Solar-Pro3 | 3,819 | 114 | 806 |
| Gemma 4 E2B | 8 | 0 | 1 |
| Gemma 3 4B | 8 | 0 | 1 |
| Phi-4 mini | 3 | 0 | 1 |
| EXAONE 3.5 | 197 | 0 | 0 |

이 비교는 모델의 생성 품질 평가가 아닙니다. tokenizer 구조에서 주의해야 할 지점을 본 것입니다. 그래도 한 가지는 분명합니다.

이번 현상은 한국어를 하는 모델이면 모두 같은 방식으로 겪는 문제가 아닙니다. Solar-Pro3 tokenizer가 특히 긴 한국어 도메인 어절을 더 적극적으로 합치는 쪽에 가깝습니다.

## Pro2에서 Pro3로 넘어가며 무엇이 바뀌었나

처음에는 Solar-Pro2와 Solar-Pro3가 같은 계열이니 tokenizer도 비슷할 것으로 생각했습니다. 하지만 실제 artifact를 비교해 보니 그렇지 않았습니다.

둘 다 vocab size는 196,608입니다. 하지만 내부는 크게 다릅니다.

| 비교 항목 | Pro2 vs Pro3 |
|---|---:|
| raw token overlap | 55.3% |
| same raw token + same id | 791개 |
| decoded token overlap | 55.3% |
| same decoded token + same id | 806개 |
| merge overlap | 30.7% |
| same merge + same rank | 2개 |

vocab size만 같을 뿐, 사실상 다른 tokenizer라고 봐야 합니다.

반면 Pro3 tokenizer와 Solar-Open-100B tokenizer는 완전히 동일했습니다.

| 비교 항목 | Pro3 vs Solar-Open-100B |
|---|---:|
| raw token overlap | 100% |
| same raw token + same id | 196,608 |
| merge overlap | 100% |
| same merge + same rank | 192,256 |

해당 phrase에서도 차이가 분명합니다.

```text
Pro2:
어떤 경우 법인세효과가 있을까?
-> ['어떤', ' 경우', ' 법인세', '효과가', ' 있을까', '?']

Pro3:
어떤 경우 법인세효과가 있을까?
-> ['어떤', ' 경우', ' 법인세효과가', ' 있을까', '?']
```

Pro2에서는 ` 법인세효과가`가 ` 법인세 + 효과가`로 남습니다. Pro3에서는 `[195496]` 하나로 합쳐집니다.

금융/회계 표현에서도 같은 경향이 보입니다.

```text
Pro2:
 매도가능증권평가손익
-> [' 매', '도가', '능', '증권', '평가', '손익']

Pro3:
 매도가능증권평가손익
-> [' 매도가능증권평가손익']
```

Pro3는 도메인 복합어를 훨씬 적극적으로 단일 토큰화합니다.

수치로 봐도 그렇습니다.

| 항목 | Pro2 | Pro3 |
|---|---:|---:|
| domain matched tokens | 295 | 2,522 |
| leading-space domain tokens | 207 | 1,594 |
| leading-space domain tokens without bare counterpart | 131 | 1,065 |
| domain hint 포함 주의 후보 | 31 | 806 |
| score >= 8 후보 | 18 | 114 |

이 정도면 Pro2에서 Pro3로 넘어가며 tokenizer의 도메인 압축 정책이 크게 바뀌었다고 보는 것이 자연스럽습니다.

## 코퍼스 비율의 영향

여기서 코퍼스 이야기를 하지 않을 수 없습니다.

Upstage의 [Solar Open Technical Report](https://arxiv.org/abs/2601.07022)는 tokenizer가 custom byte-level BPE이며, Korean과 target domain을 oversampling했다고 설명합니다. tokenizer 학습 데이터에는 Finance, Legal, Medical 문서가 4% 포함되어 있습니다. 반면 pretraining corpus 전체에서 명시된 domain-specific Finance/Medical/Legal은 0.4T / 19.7T, 약 2%입니다.

이 숫자만으로 모든 원인을 확정할 수는 없습니다. 하지만 지금 관찰한 현상과는 잘 맞습니다.

여기서 개인 경험을 조금 덧붙이면, 한국어 모델을 만들 때 가장 먼저 찾는 공개 코퍼스가 AI Hub 자료입니다. 양도 많고, 라이선스와 출처가 비교적 명확하고, 분야별로 정리되어 있기 때문입니다. 한국어 모델을 만들려고 하면 자연스럽게 먼저 들여다보게 되는 자료입니다.

다만 AI Hub 자료에는 특징이 있습니다. 정부 주도로 진행한 특성 상 웹 문서, 대화체, 일상어보다 정부 문서, 법률 문서, 정책 자료, 국회 회의록, 공공기관 보고서, 전문 분야 문서의 비중이 높습니다. 물론 AI Hub 안에도 다양한 데이터가 있지만, 전체를 큰 덩어리로 가져와 쓰면 일반 웹 한국어 분포와는 다른 방향으로 코퍼스가 기울 수 있습니다.

특히 금융, 법률, 회계 쪽 자료는 문체가 상당히 다릅니다. 일반적인 한국어 문장보다 긴 명사구가 많고, 조사까지 붙은 전문 표현이 반복됩니다.

```text
법인세비용차감전순이익과
기타포괄손익누계액으로
당기손익인식금융자산으로
상각후원가측정금융자산으로
독점규제및공정거래에관한법률상의
```

BPE 입장에선 이런 문자열이 매력적입니다. 자주 반복되고, 긴 span을 하나로 줄이면 token count가 줄어듭니다. 특히 196K처럼 큰 vocab을 쓰면 이런 tail phrase를 많이 담을 수 있습니다.

여기서 중요한 건 토크나이저 학습에서 코퍼스의 언어 비율만큼이나 각 언어 안의 도메인 비율도 중요하다는 점입니다.

예를 들어, 한국어 비율을 20%로 맞췄을 때 그 안에 뉴스가 얼마나 들어가는지, 커뮤니티 글이 얼마나 들어가는지, 문학이 얼마나 들어가는지, 법률 문서가 얼마나 들어가는지, 공공기관 문서가 얼마나 들어가는지에 따라 vocab의 구성이 완전히 달라집니다.

토크나이저는 코퍼스를 보고 "무엇을 하나의 단위로 볼 것인가"를 정합니다. 따라서 도메인 비율을 어떻게 설정하느냐에 따라 모델이 앞으로 보게 될 세계의 지도가 달라집니다. 일상어 중심의 지도를 만들 수도 있고, 법률과 회계 문서의 긴 어절이 촘촘히 박힌 지도를 만들 수도 있습니다.

물론 여기서 조심해야 합니다. 공개 정보만으로 Upstage가 특정 AI Hub 데이터셋을 사용했다고 단정할 수는 없습니다. 이 글에서 말하는 것은 특정 데이터셋 지목이 아닙니다.

더 정확히는 이렇습니다.

> AI Hub의 금융/회계/법률 데이터와 같은 코퍼스 구성은 이번 현상이 나타나기 쉬운 조건을 잘 보여준다.  
> Solar-Pro3 tokenizer의 vocab에서도 그런 도메인 phrase가 대량으로 관찰된다.  
> 따라서 이 현상은 특정 데이터셋 하나라기보다, 일반 한국어 분포와 다른 도메인 문서 비율이 tokenizer 학습에 강하게 반영되면서 생긴 편중 현상으로 보는 것이 타당하다.

모델 학습 corpus와 tokenizer 학습 corpus가 완전히 같을 필요는 없습니다. 하지만 tokenizer가 만들어내는 token 단위는 모델이 실제로 배울 수 있는 단위여야 합니다. 압축률만 보고 긴 token을 많이 만들면, 특히 tail token에서 영향이 드러날 수 있습니다.

큰 모델도 예외는 아닙니다. 큰 모델은 더 많은 것을 흡수할 수 있지만, 단일 tail token이 충분히 학습되지 않으면 더 작은 의미 단위로 나누어 이해할 수 없습니다. `법인세`와 `효과`를 따로 보면 이해할 수 있는 모델도, `[195496]` 하나만 보면 원래 의미에서 벗어날 수 있습니다.

## 그래서 원인은 무엇인가

현재까지의 결과를 하나로 묶으면 이렇게 볼 수 있습니다.

```text
1. Pro3/Solar-Open 계열 tokenizer는 Pro2보다 한국어 도메인 phrase를 훨씬 적극적으로 합친다.
2. 그 결과 ' 법인세효과가' 같은 긴 선행 공백 어절이 high-rank tail token이 되었다.
3. 이 token은 vocab에는 있지만 모델 본체에서 의미가 충분히 안정화되지 않았다.
4. 앞 단어 뒤에 이어질 때는 이 token path를 타고, 문장 처음에 오거나 명시적으로 띄어 쓰면 분해된 subtoken path를 탄다.
5. 따라서 공백 하나로 답변의 의미가 크게 바뀐다.
```

이 현상을 일반적인 hallucination으로만 부르면 핵심을 놓칩니다. 모델은 법인세를 모르는 것이 아닙니다. 같은 모델이 `법인세 효과가`에는 정상적으로 답합니다.

더 정확한 이름은 tokenizer-model alignment issue에 가깝습니다.

```text
tokenizer는 압축을 위해 긴 도메인 어절을 atomic token으로 만들었다.
하지만 model은 그 atomic token을 충분히 의미 있는 단위로 학습하지 못한 것으로 보인다.
```

## 그렇다면 Solar-Open2/Pro4에서는 어땠나

이제 다시 출발점으로 돌아가 보겠습니다. 이 글을 쓰게 된 계기는 Solar-Open2였습니다. Solar-Open2는 독자 AI 파운데이션 모델 프로젝트에 참여 중인 Upstage사가 개발한 최신 모델입니다. 실험은 timelyai.io를 사용했습니다.

Solar-Open2에 같은 질문을 던져봤습니다.

```text
어떤 경우 법인세효과가 있을까?
```

응답은 Solar-Pro3처럼 `Kami` 같은 전혀 무관한 단어로 이동하지는 않았습니다. 다만 `법인세 효과`로 바로 고정되지는 않았습니다. 답변은 이렇게 시작했습니다.

```text
좋은 질문입니다. "세액효과"라는 표현이 약간 모호할 수 있어,
일반적으로 세금 관련 효과(조세효과)가 발생하는 주요 상황들을 중심으로 설명드리겠습니다.
```

즉 모델은 `법인세효과가`를 곧바로 `법인세 효과`로 처리하기보다, `세액효과` 또는 `조세효과`라는 더 넓은 말로 바꾸어 처리했습니다. 이후 답변은 소득세, 양도소득세, 부가가치세, 법인세, 국제조세, 이연법인세 등을 설명했습니다. 세금 문맥 안에는 남아 있었지만, 질문의 초점인 `법인세 효과`에 바로 고정됐다고 보기는 어려웠습니다.

대조 질문은 다르게 동작했습니다.

```text
어떤 경우 법인세 효과가 있을까?
```

이 경우 Solar-Open2는 법인세 과세효과, 손금산입, 세액공제, 합병·분할, 이연법인세, 국제조세, 자금조달의 tax shield까지 정상적인 법인세 문맥으로 자세히 답했습니다.

따라서 Solar-Open2의 결과는 중간 정도로 볼 수 있습니다.

```text
Solar-Pro3:
  법인세효과가 -> Kami / 효과성 / 누적효과 등으로 강하게 어긋남

Solar-Open2:
  법인세효과가 -> 세액효과 / 조세효과로 넓게 바꾸어 해석
  법인세 효과가 -> 정확한 법인세 문맥으로 답변
```

즉 Solar-Open2에서도 해당 현상이 완전히 사라졌다고 말하기는 어렵습니다. 다만 Solar-Pro3처럼 의미가 전혀 다른 방향으로 크게 벗어나지는 않고, 세금이라는 큰 범주 안에서 질문을 넓게 다시 해석하는 정도에 가깝습니다.

이 차이는 오히려 원인 분석과 잘 맞습니다. 현상이 tokenizer path 하나만으로 결정되는 것은 아닙니다. tokenizer가 민감한 경로를 만들더라도, 모델 본체가 그 token을 얼마나 잘 학습했는지, instruction tuning이 그 표현을 어떻게 다뤘는지에 따라 출력 양상은 달라질 수 있습니다. Solar-Open2는 세금이라는 상위 문맥은 유지했지만, `법인세효과가`를 정확한 법인세 표현으로 바로 처리했다고 보기는 어려웠습니다.

## 어떻게 해결할 수 있을까

먼저 구분해야 할 것이 있습니다.

이번 실험에서 실제로 확인한 것은 **해당 token path를 피하면 답변이 안정화된다**는 점입니다. 반대로 모델 weight나 서버 tokenizer를 직접 수정하는 방법은 제가 실험으로 검증한 것이 아니라, 이 원인 분석에서 도출되는 구조적 해결 제안입니다.

검증된 것은 다음입니다.

```text
어떤 경우 법인세효과가 있을까?
-> [41170, 5577, 195496, 51490, 4126]
-> Console/API에서 의미가 달라짐

어떤 경우 법인세 효과가 있을까?
-> [41170, 5577, 9915, 23183, 51490, 4126]
-> 정상 답변

법인세효과가 발생하는 경우를 설명해줘.
-> [7131, 32372, ...]
-> 정상 답변

어떤 경우
법인세효과가 있을까?
-> [..., 4294, 7131, 32372, ...]
-> 정상 답변
```

또 NBSP(non-breaking space: U+00A0)를 이용한 대조 실험에서도 `[195496]`를 피하는 것을 확인했습니다.

```text
어떤 경우 법인세효과가 있을까?
-> [41170, 5577, 4905, 7131, 32372, 51490, 4126]
```

즉 운영 단계에서 당장 쓸 수 있는 완화책은 입력을 명시적으로 띄어 쓰거나, 줄 바꿈 등으로 `[195496]` 경로를 피하는 것입니다. 다만 이것은 입력 단계의 완화책입니다. 특정 문자열 하나만 고치는 방식으로는 같은 구조의 다른 token을 충분히 다루기 어렵습니다.

그래서 아래 해결책들은 검증 여부를 나누어 보는 것이 좋습니다.

### 1. 검증된 완화책: 안전한 token path로 보내기

가장 현실적인 대응은 모델 호출 전에 입력을 검사하고, 해당 token path를 피하도록 바꾸는 것입니다.

예를 들어:

```text
법인세효과가 -> 법인세 효과가
```

또는:

```text
어떤 경우 법인세효과가 있을까?
-> 어떤 경우
   법인세효과가 있을까?
```

이 방식은 실제 API/Console 실험에서 정상 답변으로 돌아오는 것을 확인했습니다. 다만 사용자 입력을 바꾸는 방식이므로, 제품에 적용하려면 원문 보존과 표시 문자열을 어떻게 처리할지 별도로 설계해야 합니다.

### 2. 부분적으로 확인 가능한 제안: inference-time merge blocklist

입력 문자열을 직접 바꾸는 대신, tokenizer의 BPE merge 과정에서 민감한 merge를 관리하는 방법도 생각할 수 있습니다.

예를 들어 이런 token을 우선 검토 대상으로 삼을 수 있습니다.

```text
decoded token이 ASCII space로 시작
한글 포함
길이 5자 이상
high-rank tail token
bare counterpart 없음
도메인 긴 명사구 또는 조사 결합형
```

이 방향은 tokenizer trace로는 타당성을 확인할 수 있습니다. 실제로 `[195496]`는 다음 late merge 때문에 생깁니다.

```text
 법인세효과 + 가 ->  법인세효과가
```

이 merge를 막으면 ` 법인세효과가`는 더 작은 하위 token sequence로 남게 됩니다. 그리고 우리가 이미 확인한 것처럼 하위 token sequence로 들어간 질문은 정상 답변을 냅니다.

다만 이것을 실제 Upstage 서버 tokenizer에 적용해 본 것은 아닙니다. 따라서 이 항목은 "검증된 해결책"이라기보다, 현재 증거로 보아 가장 직접적인 provider-side 완화책 후보입니다.

### 3. 검증하지 못한 구조적 제안: compositional embedding repair

모델 제공자라면 민감한 token embedding을 보정하는 방법도 검토할 수 있습니다.

```text
[195496] = " 법인세효과가"
safe path = [" 법인세", "효과가"] 또는 [" 법인세", "효과", "가"]
```

그다음 `[195496]`의 embedding을 safe path embedding 조합에 가깝게 보정합니다. 

이 방법은 이론적으론 원인에 잘 맞습니다. 관찰된 현상이 `[195496]`가 `법인세`와 `효과가`의 조합 의미를 충분히 보존하지 못하는 데서 나오기 때문입니다. 하지만 이것은 모델 embedding matrix에 접근해야 검증할 수 있습니다. 공개 API만으로는 확인할 수 없습니다.

### 4. 검증하지 못한 구조적 제안: tokenization-invariance distillation

가장 중요한 것은 tokenization path가 달라도 같은 의미를 내도록 학습하는 것입니다.

```text
어떤 경우 법인세효과가 있을까?
어떤 경우 법인세 효과가 있을까?
법인세효과가 발생하는 경우를 설명해줘.
```

이 세 질문은 같은 의미를 가져야 합니다. 모델의 next-token distribution 또는 최종 답변이 서로 비슷해지도록 SFT/KL distillation을 걸 수 있습니다.

이 역시 공개 API만으로 검증한 해결책은 아닙니다. 다만 현상의 성격상 단순히 회계 corpus를 더 넣는 것보다 더 맞는 처방일 수 있습니다. 관찰된 것은 지식 부족이라기보다 tokenization path 간 의미 불변성 부족에 가깝기 때문입니다.

### 5. 장기 제안: 다음 tokenizer의 학습 정책 변경

장기적으로는 tokenizer 학습 단계에서 이런 후보를 관리해야 합니다.

특히 다음 형태를 조심해야 합니다.

```text
' X'는 단일 token인데
'X'는 단일 token이 아니거나 안정적인 짧은 sequence가 아닌 경우
```

이런 token을 orphan leading-space token이라고 부를 수 있습니다. 한국어에서는 더 민감합니다. 조사와 어미가 붙은 긴 어절이 많고, 공시/법률 문서에는 같은 template 문구가 반복되기 때문입니다.

merge 후보를 고를 때 raw frequency만 보면 안 됩니다. 문서 다양성, source 다양성, 문맥 entropy, suffix 다양성, domain 편중을 같이 봐야 합니다.

## 마무리

이번 현상은 작아 보이지만, 한국어 모델을 볼 때 토크나이저까지 함께 살펴봐야 한다는 점을 다시 떠올리게 했습니다.

한국어 모델을 만들 때 모델 크기, 데이터 규모, 도메인 보강은 모두 중요합니다. 다만 그 과정에서 토크나이저가 문장을 어떤 단위로 모델에 넘겨주는지도 함께 봐야 합니다.

토크나이저는 데이터와 모델 사이에서 입력의 단위를 정합니다.

토크나이저가 너무 잘게 쪼개면 문장이 길어지고 효율이 떨어집니다. 반대로 너무 적극적으로 합치면 모델이 배워야 할 atomic token이 늘어납니다. 특히 도메인 문서가 과대표집된 상태에서 큰 vocab을 쓰면, 일반 한국어에서는 거의 쓰이지 않는 긴 전문 어절이 tail token으로 들어갈 수 있습니다.

`법인세효과가` 사례는 그 균형을 살펴보게 만든 작은 단서였습니다.

Pro2에서는 ` 법인세 + 효과가`로 남아 있던 표현이, Pro3에서는 ` 법인세효과가` 하나로 합쳐졌습니다. token count는 줄었지만 의미 조합 경로는 줄어들었습니다. 그리고 모델은 그 하나의 token을 충분히 안정적인 의미 단위로 배우지 못한 것으로 보입니다.

그래서 저는 이 현상을 단일 구현 오류라기보다, tokenizer corpus와 model corpus 사이의 비율 문제, 그리고 compression efficiency와 learnability 사이의 균형 문제로 추측합니다.

데이터가 중요하다는 말은 이제 너무 익숙합니다. 하지만 그 데이터가 tokenizer에 어떤 비율로 들어가는지, 어떤 단어를 하나의 token으로 만들고 어떤 단어를 조합 가능한 단위로 남길지도 그만큼 중요합니다.

토크나이저는 눈에 잘 띄지 않지만, 모델이 세상을 바라보는 모양을 정합니다. 이번에는 그 차이가 ` 법인세효과가`라는 작은 조각에서 드러났습니다.
